## Overview

레지스트리 네임스페이스는 `@` 로 시작하며, 여러 출처의 자원을 정리하고 참조하는 방법입니다. 자원은 종류를 가리지 않습니다. 컴포넌트·라이브러리·유틸리티·훅·AI 프롬프트·설정 파일·테마 등 무엇이든 됩니다. 예를 들면 이렇습니다.

- `@shadcn/button` — shadcn 레지스트리의 UI 컴포넌트
- `@v0/dashboard` — v0 레지스트리의 대시보드 컴포넌트
- `@ai-elements/input` — AI elements 레지스트리의 프롬프트 입력
- `@acme/auth-utils` — 사내 비공개 레지스트리의 인증 유틸리티
- `@ai/chatbot-rules` — AI 자원 레지스트리의 프롬프트 규칙
- `@themes/dark-mode` — 테마 레지스트리의 테마 설정

## Decentralized Namespace System

네임스페이스 체계는 일부러 분산형으로 설계했습니다. 오픈소스 네임스페이스를 위한 [중앙 색인](/docs/registry/registry-index)이 있긴 하지만, 원하는 네임스페이스를 자유롭게 만들어 써도 됩니다.

분산형이라 조직에 맞는 방식으로 자원을 자유롭게 정리할 수 있습니다.

목적에 따라 레지스트리를 여러 개 만들 수 있습니다.

```json title="components.json" showLineNumbers
{
  "registries": {
    "@acme-ui": "https://registry.acme.com/ui/{name}.json",
    "@acme-docs": "https://registry.acme.com/docs/{name}.json",
    "@acme-ai": "https://registry.acme.com/ai/{name}.json",
    "@acme-themes": "https://registry.acme.com/themes/{name}.json",
    "@acme-internal": {
      "url": "https://internal.acme.com/registry/{name}.json",
      "headers": {
        "Authorization": "Bearer ${INTERNAL_TOKEN}"
      }
    }
  }
}
```

그러면 이런 것이 가능합니다.

- **종류별로**: UI 컴포넌트·문서·AI 자원 등을 나눕니다
- **팀별로**: 팀마다 자기 레지스트리를 관리합니다
- **공개 범위별로**: 공개 자원과 비공개 자원을 나눕니다
- **버전별로**: 안정판과 실험판 레지스트리를 나눕니다
- **이름 충돌 없음**: 중앙 권한이 없으니 네임스페이스가 겹칠 걱정이 없습니다

### Examples of Multi-Registry Setups

#### By Resource Type

```json title="components.json" showLineNumbers
{
  "@components": "https://cdn.company.com/components/{name}.json",
  "@hooks": "https://cdn.company.com/hooks/{name}.json",
  "@utils": "https://cdn.company.com/utils/{name}.json",
  "@prompts": "https://cdn.company.com/ai-prompts/{name}.json"
}
```

#### By Team or Department

```json title="components.json" showLineNumbers
{
  "@design": "https://create.company.com/registry/{name}.json",
  "@engineering": "https://eng.company.com/registry/{name}.json",
  "@marketing": "https://marketing.company.com/registry/{name}.json"
}
```

#### By Stability

```json title="components.json" showLineNumbers
{
  "@stable": "https://registry.company.com/stable/{name}.json",
  "@latest": "https://registry.company.com/beta/{name}.json",
  "@experimental": "https://registry.company.com/experimental/{name}.json"
}
```

## Getting Started

### Installing Resources

설정해 두면 네임스페이스 문법으로 자원을 설치합니다.

```bash
npx shadcn@latest add @v0/dashboard
```

여러 자원을 한 번에 설치할 수도 있습니다.

```bash
npx shadcn@latest add @acme/header @lib/auth-utils @ai/chatbot-rules
```

### Quick Configuration

`components.json` 에 레지스트리를 추가합니다.

```json title="components.json"
{
  "registries": {
    "@v0": "https://v0.dev/chat/b/{name}",
    "@acme": "https://registry.acme.com/resources/{name}.json"
  }
}
```

그다음 설치를 시작합니다.

```bash
npx shadcn@latest add @acme/button
```

## Registry Naming Convention

레지스트리 이름은 아래 규칙을 지켜야 합니다.

- `@` 로 시작합니다
- 영문자·숫자·하이픈·밑줄만 씁니다
- 올바른 예: `@v0`·`@acme-ui`·`@my_company`

자원을 참조하는 형식은 `@namespace/resource-name` 입니다.

## GitHub and Namespaces

GitHub 레지스트리 주소와 네임스페이스는 서로 다른 문제를 풉니다.

레지스트리가 공개 GitHub 저장소이고 사용자가 `components.json` 설정 없이
설치하게 하고 싶다면 GitHub 주소를 쓰세요.

```bash
npx shadcn@latest add acme/ui/button
```

고정된 별칭, 직접 운영하는 호스팅, 인증, 요청 헤더, 쿼리 파라미터, 비공개
레지스트리가 필요하다면 네임스페이스를 쓰세요.

```bash
npx shadcn@latest add @acme/button
```

자세한 내용은 [GitHub 레지스트리](/docs/registry/github) 문서를 보세요.

## Configuration

네임스페이스 레지스트리는 `components.json` 의 `registries` 필드에서 설정합니다.

### Basic Configuration

가장 단순한 방법은 주소 템플릿 문자열을 적는 것입니다.

```json title="components.json"
{
  "registries": {
    "@v0": "https://v0.dev/chat/b/{name}",
    "@acme": "https://registry.acme.com/resources/{name}.json",
    "@lib": "https://lib.company.com/utilities/{name}",
    "@ai": "https://ai-resources.com/r/{name}.json"
  }
}
```

> **참고:** `npx shadcn@latest add @namespace/resource-name` 을 돌리면 주소의 `{name}` 자리에 자원 이름이 자동으로 들어갑니다. 예를 들어 `@acme/button` 은 `https://registry.acme.com/resources/button.json` 이 됩니다. 자세한 내용은 [URL Pattern System](#url-pattern-system) 을 보세요.

### Advanced Configuration

인증이나 추가 파라미터가 필요한 레지스트리라면 객체 형식을 쓰세요.

```json title="components.json"
{
  "registries": {
    "@private": {
      "url": "https://api.company.com/registry/{name}.json",
      "headers": {
        "Authorization": "Bearer ${REGISTRY_TOKEN}",
        "X-API-Key": "${API_KEY}"
      },
      "params": {
        "version": "latest",
        "format": "json"
      }
    }
  }
}
```

> **참고:** `${VAR_NAME}` 형식으로 쓴 환경 변수는 실행 환경(process.env)에서 자동으로 채워집니다. 주소·헤더·파라미터 어디서나 됩니다. 예를 들어 `${REGISTRY_TOKEN}` 은 `process.env.REGISTRY_TOKEN` 값으로 바뀝니다. 자세한 내용은 [Authentication & Security](#authentication--security) 를 보세요.

### URL Pattern System

레지스트리 주소는 아래 자리표시자를 지원합니다.

### `{name}` Placeholder (required)

`{name}` 자리에는 자원 이름이 들어갑니다.

```json title="components.json" showLineNumbers
{
  "@acme": "https://registry.acme.com/{name}.json"
}
```

`@acme/button` 을 설치하면 주소는 `https://registry.acme.com/button.json` 이 됩니다.
`@acme/auth-utils` 를 설치하면 `https://registry.acme.com/auth-utils.json` 이 됩니다.

### `{style}` Placeholder (optional)

`{style}` 자리에는 현재 스타일 설정이 들어갑니다.

```json
{
  "@themes": "https://registry.example.com/{style}/{name}.json"
}
```

스타일이 `new-york` 이면 `@themes/card` 는 `https://registry.example.com/new-york/card.json` 으로 풀립니다.

스타일 자리표시자는 선택입니다. 같은 자원을 여러 버전으로 내보내고 싶을 때 씁니다. 예를 들어 스타일마다 다른 컴포넌트를 내보낼 수 있습니다.

## Authentication & Security

### Environment Variables

자격 증명은 환경 변수에 안전하게 둡니다.

```json title="components.json"
{
  "registries": {
    "@private": {
      "url": "https://api.company.com/registry/{name}.json",
      "headers": {
        "Authorization": "Bearer ${REGISTRY_TOKEN}"
      }
    }
  }
}
```

그다음 환경 변수를 설정합니다.

```bash title=".env.local"
REGISTRY_TOKEN=your_secret_token_here
```

### Authentication Methods

#### Bearer Token (OAuth 2.0)

```json
{
  "@github": {
    "url": "https://api.github.com/repos/org/registry/contents/{name}.json",
    "headers": {
      "Authorization": "Bearer ${GITHUB_TOKEN}"
    }
  }
}
```

#### API Key in Headers

```json title="components.json" showLineNumbers
{
  "@private": {
    "url": "https://api.company.com/registry/{name}",
    "headers": {
      "X-API-Key": "${API_KEY}"
    }
  }
}
```

#### Basic Authentication

```json title="components.json" showLineNumbers
{
  "@internal": {
    "url": "https://registry.company.com/{name}.json",
    "headers": {
      "Authorization": "Basic ${BASE64_CREDENTIALS}"
    }
  }
}
```

#### Query Parameter Authentication

```json title="components.json" showLineNumbers
{
  "@secure": {
    "url": "https://registry.example.com/{name}.json",
    "params": {
      "api_key": "${API_KEY}",
      "client_id": "${CLIENT_ID}",
      "signature": "${REQUEST_SIGNATURE}"
    }
  }
}
```

#### Multiple Authentication Methods

인증 방식을 여러 개 요구하는 레지스트리도 있습니다.

```json title="components.json" showLineNumbers
{
  "@enterprise": {
    "url": "https://api.enterprise.com/v2/registry/{name}",
    "headers": {
      "Authorization": "Bearer ${ACCESS_TOKEN}",
      "X-API-Key": "${API_KEY}",
      "X-Workspace-Id": "${WORKSPACE_ID}"
    },
    "params": {
      "version": "latest"
    }
  }
}
```

### Security Considerations

네임스페이스 레지스트리, 특히 서드파티나 공개 레지스트리를 다룰 때는 보안이 가장 중요합니다. 이렇게 다룹니다.

### Resource Validation

레지스트리에서 받은 자원은 설치 전에 항목 스키마로 검증합니다. 그래서 이런 것이 보장됩니다.

- **구조 검증**: 자원이 정해진 JSON 스키마를 따라야 합니다
- **타입 안전**: 자원 종류(`registry:ui`·`registry:lib` 등)를 검증합니다
- **임의 코드 실행 없음**: 자원은 데이터 파일이지 실행되는 스크립트가 아닙니다

### Environment Variable Security

인증에 쓰는 환경 변수는 이렇게 다룹니다.

- **기록하지 않음**: CLI 는 환경 변수 값을 기록하거나 보여 주지 않습니다
- **필요할 때만 채움**: 필요한 순간에만 값을 채우고 저장하지 않습니다
- **레지스트리별 분리**: 레지스트리마다 인증 맥락을 따로 둡니다

안전한 설정 예시입니다.

```json title="components.json" showLineNumbers
{
  "registries": {
    "@private": {
      "url": "https://api.company.com/registry/{name}.json",
      "headers": {
        "Authorization": "Bearer ${PRIVATE_REGISTRY_TOKEN}"
      }
    }
  }
}
```

실제 토큰을 버전 관리에 커밋하지 마세요. `.env.local` 을 쓰세요.

```bash title=".env.local"
PRIVATE_REGISTRY_TOKEN=actual_token_here
```

### HTTPS Enforcement

레지스트리 주소에는 반드시 HTTPS 를 쓰기를 권합니다.

- **암호화된 전송**: 중간자 공격을 막습니다
- **인증서 검증**: 진짜 레지스트리에 연결하고 있는지 확인합니다
- **자격 증명 보호**: 헤더와 토큰이 전송 중 암호화됩니다

```json title="components.json" showLineNumbers
{
  "registries": {
    "@secure": "https://registry.example.com/{name}.json", // ✅ Good
    "@insecure": "http://registry.example.com/{name}.json" // ❌ Avoid
  }
}
```

### Content Security

레지스트리의 자원은 코드가 아니라 데이터로 다룹니다.

1. **JSON 파싱만**: 자원은 올바른 JSON 이어야 합니다
2. **스키마 검증**: 레지스트리 항목 스키마와 맞아야 합니다
3. **경로 제한**: 파일은 설정된 경로에만 쓸 수 있습니다
4. **스크립트 실행 없음**: CLI 는 자원에 담긴 코드를 실행하지 않습니다

### Registry Trust Model

네임스페이스 체계는 신뢰를 전제로 동작합니다.

- **설치하는 것은 신뢰해야 합니다**: 믿을 수 있는 레지스트리만 설정에 넣으세요
- **명시적 설정**: 레지스트리는 `components.json` 에 직접 적어야 합니다
- **자동 탐색 없음**: CLI 가 레지스트리를 알아서 추가하는 일은 없습니다
- **의존성 투명성**: 모든 의존성이 항목에 분명히 적혀 있습니다

### Best Practices for Registry Operators

직접 레지스트리를 운영한다면 이렇게 하세요.

1. **항상 HTTPS**: 레지스트리 내용을 HTTP 로 내보내지 마세요
2. **인증 붙이기**: 비공개 레지스트리에는 API 키나 토큰을 요구하세요
3. **요청 제한**: 남용되지 않도록 보호하세요
4. **내용 검증**: 내보내기 전에 자원을 검증하세요

안전한 레지스트리 설정 예시입니다.

```json title="components.json" showLineNumbers
{
  "@company": {
    "url": "https://registry.company.com/v1/{name}.json",
    "headers": {
      "Authorization": "Bearer ${COMPANY_TOKEN}",
      "X-Registry-Version": "1.0"
    }
  }
}
```

### Inspecting Resources Before Installation

CLI 는 무엇이 설치되는지 그대로 보여 줍니다. 아래 명령으로 항목의 내용을 볼 수 있습니다.

```bash
npx shadcn@latest view @acme/button
```

항목의 내용이 콘솔에 출력됩니다.

## Dependency Resolution

### Basic Dependency Resolution

자원은 서로 다른 레지스트리에 걸쳐 의존할 수 있습니다.

```json title="registry-item.json" showLineNumbers
{
  "name": "dashboard",
  "type": "registry:block",
  "registryDependencies": [
    "@shadcn/card", // From default registry
    "@v0/chart", // From v0 registry
    "@acme/data-table", // From acme registry
    "@lib/data-fetcher", // Utility library
    "@ai/analytics-prompt" // AI prompt resource
  ]
}
```

CLI 가 각 레지스트리에서 의존성을 모두 풀어 설치합니다.

### Advanced Dependency Resolution

레지스트리를 만들거나 서드파티 자원을 고쳐 써야 한다면 의존성이 내부에서 어떻게 풀리는지 알아 두는 게 좋습니다.

### How Resolution Works

`npx shadcn@latest add @namespace/resource` 를 돌리면 CLI 는 이렇게 동작합니다.

1. **레지스트리 맥락을 비우고** 새로 시작합니다
2. 지정된 레지스트리에서 **주 자원을 가져옵니다**
3. 각 레지스트리에서 **의존성을 재귀로 풀어냅니다**
4. 설치 순서가 맞도록 **위상 정렬**합니다
5. 대상 경로를 기준으로 **파일 중복을 제거**합니다(마지막 것이 이깁니다)
6. 설정(tailwind·cssVars·css·envVars)을 **깊게 병합**합니다

그래서 아래 명령을 돌리면,

```bash
npx shadcn@latest add @acme/auth @custom/login-form
```

`@custom/login-form` 의 `login-form.ts` 가 나중에 풀리므로 `@acme/auth` 의 것을 덮어씁니다.

### Overriding Third-Party Resources

이 해석 순서를 이용하면 서드파티 자원을 덮어쓸 수 있습니다. 직접 만든 자원의 `registryDependencies` 에 넣고 원하는 값으로 덮으면 됩니다.

#### Example: Customizing a Third-Party Button

외부 레지스트리의 버튼을 고쳐 쓴다고 해 봅시다.

**1. 원본 버튼** (`@vendor/button`)

```json title="button.json" showLineNumbers
{
  "name": "button",
  "type": "registry:ui",
  "files": [
    {
      "path": "components/ui/button.tsx",
      "type": "registry:ui",
      "content": "// Vendor's button implementation\nexport function Button() { ... }"
    }
  ],
  "cssVars": {
    "light": {
      "--button-bg": "blue"
    }
  }
}
```

**2. 덮어쓸 항목 만들기** (`@my-company/custom-button`)

```json title="custom-button.json" showLineNumbers
{
  "name": "custom-button",
  "type": "registry:ui",
  "registryDependencies": [
    "@vendor/button" // Import original first
  ],
  "cssVars": {
    "light": {
      "--button-bg": "purple" // Override the color
    }
  }
}
```

**3. 만든 버전을 설치**

```bash
npx shadcn@latest add @my-company/custom-button
```

그러면 `@vendor/button` 의 원본 버튼을 설치한 뒤 `cssVars` 를 여러분이 정한 값으로 덮습니다.

### Advanced Override Patterns

#### Extending Without Replacing

원본은 그대로 두고 확장만 더합니다.

```json title="extended-table.json" showLineNumbers
{
  "name": "extended-table",
  "registryDependencies": ["@vendor/table"],
  "files": [
    {
      "path": "components/ui/table-extended.tsx",
      "content": "import { Table } from '@vendor/table'\n// Add your extensions\nexport function ExtendedTable() { ... }"
    }
  ]
}
```

`@vendor/table` 의 원본 표를 설치한 뒤 확장을 `components/ui/table-extended.tsx` 에 더합니다.

#### Partial Override (Multi-file Resources)

복합 컴포넌트에서 특정 파일만 덮어씁니다.

```json title="custom-auth.json" showLineNumbers
{
  "name": "custom-auth",
  "registryDependencies": [
    "@vendor/auth" // Has multiple files
  ],
  "files": [
    {
      "path": "lib/auth-server.ts",
      "type": "registry:lib",
      "content": "// Your custom auth server"
    }
  ]
}
```

### Resolution Order Example

여러 자원에 기대는 `@custom/dashboard` 를 설치하면,

```json title="dashboard.json" showLineNumbers
{
  "name": "dashboard",
  "registryDependencies": [
    "@shadcn/card", // 1. Resolved first
    "@vendor/chart", // 2. Resolved second
    "@custom/card" // 3. Resolved last (overrides @shadcn/card)
  ]
}
```

해석 순서는 이렇습니다.

1. `@shadcn/card` — `components/ui/card.tsx` 에 설치
2. `@vendor/chart` — `components/ui/chart.tsx` 에 설치
3. `@custom/card` — 대상이 같다면 `components/ui/card.tsx` 를 덮어씀

### Key Resolution Features

1. **출처 추적**: 자원마다 어느 레지스트리에서 왔는지 알고 있어 이름이 겹치지 않습니다
2. **순환 의존성 방지**: 순환을 자동으로 찾아 막습니다
3. **설치 순서 정리**: 의존성을 먼저 설치하고 그것을 쓰는 자원을 나중에 설치합니다

## Versioning

쿼리 파라미터로 자원에 버전을 붙일 수 있습니다. 그러면 사용자가 특정 버전에 고정하거나 다른 배포 채널을 쓸 수 있습니다.

### Basic Version Parameter

```json title="components.json" showLineNumbers
{
  "@versioned": {
    "url": "https://registry.example.com/{name}",
    "params": {
      "version": "v2"
    }
  }
}
```

그러면 `@versioned/button` 은 `https://registry.example.com/button?version=v2` 로 풀립니다.

### Dynamic Version Selection

환경 변수로 프로젝트 전체의 버전을 관리합니다.

```json title="components.json" showLineNumbers
{
  "@stable": {
    "url": "https://registry.company.com/{name}",
    "params": {
      "version": "${REGISTRY_VERSION}"
    }
  }
}
```

그러면 이런 것이 가능합니다.

- 운영에서는 `REGISTRY_VERSION=v1.2.3` 을 지정합니다
- 환경(dev·staging·prod)마다 다르게 덮어씁니다

### Semantic Versioning

범위를 지원하는 유의적 버전을 씁니다.

```json title="components.json" showLineNumbers
{
  "@npm-style": {
    "url": "https://registry.example.com/{name}",
    "params": {
      "semver": "^2.0.0",
      "prerelease": "${ALLOW_PRERELEASE}"
    }
  }
}
```

### Version Resolution Best Practices

1. 환경마다 버전을 다루려면 **환경 변수**를 씁니다
2. `${VAR:-default}` 문법으로 **적당한 기본값**을 둡니다
3. 사용자를 위해 **버전 규칙을 분명히 적어 둡니다**
4. 재현 가능한 빌드를 위해 **버전 고정**을 지원합니다
5. `/versions/{name}` 같은 **버전 조회 엔드포인트**를 둡니다
6. 캐시 헤더를 제대로 붙여 **버전별 자원을 캐시**합니다

## CLI Commands

shadcn CLI 에는 네임스페이스 레지스트리를 다루는 명령이 여럿 있습니다.

### Adding Resources

설정한 어느 레지스트리에서든 자원을 설치합니다.

```bash
# Install from a specific registry
npx shadcn@latest add @v0/dashboard

# Install multiple resources
npx shadcn@latest add @acme/button @lib/utils @ai/prompt

# Install from URL directly
npx shadcn@latest add https://registry.example.com/button.json

# Install from local file
npx shadcn@latest add ./local-registry/button.json
```

### Viewing Resources

설치 전에 항목을 들여다봅니다.

```bash
# View a resource from a registry
npx shadcn@latest view @acme/button

# View multiple resources
npx shadcn@latest view @v0/dashboard @shadcn/card

# View from URL
npx shadcn@latest view https://registry.example.com/button.json
```

`view` 는 이런 것을 보여 줍니다.

- 자원 메타데이터(이름·종류·설명)
- 의존성과 레지스트리 의존성
- 설치될 파일 내용
- CSS 변수와 Tailwind 설정
- 필요한 환경 변수

### Searching Registries

레지스트리에서 쓸 수 있는 자원을 찾습니다.

```bash
# Search a specific registry
npx shadcn@latest search @v0

# Search with query
npx shadcn@latest search @acme --query "auth"

# Search multiple registries
npx shadcn@latest search @v0 @acme @lib

# Limit results
npx shadcn@latest search @v0 --limit 10 --offset 20

# List all items (alias for search)
npx shadcn@latest list @acme
```

검색 결과에는 이런 것이 담깁니다.

- 자원 이름과 종류
- 설명
- 어느 레지스트리에서 왔는지

## Error Handling

### Registry Not Configured

설정하지 않은 레지스트리를 참조하면,

```bash
npx shadcn@latest add @non-existent/component
```

Error:

```txt
Unknown registry "@non-existent". Make sure it is defined in components.json as follows:
{
  "registries": {
    "@non-existent": "[URL_TO_REGISTRY]"
  }
}
```

### Missing Environment Variables

필요한 환경 변수가 없으면,

```txt
Registry "@private" requires the following environment variables:

  • REGISTRY_TOKEN

Set the required environment variables to your .env or .env.local file.
```

### Resource Not Found

404 Not Found:

```txt
The item at https://registry.company.com/button.json was not found. It may not exist at the registry.
```

보통 이런 경우입니다.

- 자원 이름을 잘못 적었습니다
- 그 자원이 레지스트리에 없습니다
- 레지스트리 주소 형식이 잘못됐습니다

### Authentication Failures

401 Unauthorized:

```txt
You are not authorized to access the item at https://api.company.com/button.json
Check your authentication credentials and environment variables.
```

403 Forbidden:

```txt
Access forbidden for https://api.company.com/button.json
Verify your API key has the necessary permissions.
```

## Creating Your Own Registry

네임스페이스 체계와 맞추면 어떤 자원이든 내보낼 수 있습니다. 컴포넌트·라이브러리·유틸리티·AI 프롬프트·테마·설정 등 나눌 수 있는 것이면 무엇이든 됩니다.

1. **항목 스키마 지키기**: 레지스트리는 [registry item 스키마](/docs/registry/registry-item-json)를 따르는 JSON 을 돌려줘야 합니다.

2. **주소 형식 지원**: 자원 이름이 들어갈 자리에 `{name}` 을 넣어 주소 템플릿을 만듭니다.

3. **자원 종류 정의**: `registry:ui`·`registry:lib`·`registry:ai`·`registry:theme` 처럼 알맞은 `type` 을 지정합니다.

4. **인증 처리**(필요하다면): 헤더나 쿼리 파라미터로 인증을 받습니다.

5. **네임스페이스 안내**: 사용자가 레지스트리를 설정하는 방법을 분명히 적어 둡니다.

```json title="components.json" showLineNumbers
{
  "registries": {
    "@your-registry": "https://your-domain.com/r/{name}.json"
  }
}
```

## Technical Details

### Parser Pattern

네임스페이스 파서는 아래 정규식을 씁니다.

```regex title="namespace-parser.js"
/^(@[a-zA-Z0-9](?:[a-zA-Z0-9-_]*[a-zA-Z0-9])?)\/(.+)$/
```

그래서 네임스페이스 형식이 올바른지 확인하고 컴포넌트 이름을 제대로 뽑아냅니다.

### Resolution Process

1. **파싱**: `@namespace/component` 에서 네임스페이스와 컴포넌트 이름을 뽑습니다
2. **조회**: `@namespace` 의 레지스트리 설정을 찾습니다
3. **주소 만들기**: 자리표시자를 실제 값으로 바꿉니다
4. **헤더 설정**: 설정된 인증 헤더를 붙입니다
5. **가져오기**: 풀어낸 주소에서 컴포넌트를 받습니다
6. **검증**: 응답이 항목 스키마와 맞는지 확인합니다
7. **의존성 해석**: 레지스트리 의존성을 재귀로 가져옵니다

### Cross-Registry Dependencies

컴포넌트가 여러 레지스트리에 걸쳐 의존할 때, 해석기는 이렇게 합니다.

1. 레지스트리마다 인증 맥락을 따로 유지합니다
2. 각 의존성을 원래 출처에서 풀어냅니다
3. 대상 경로를 기준으로 파일 중복을 제거합니다
4. 모든 출처의 설정(tailwind·cssVars 등)을 병합합니다

## Best Practices

1. API 키나 토큰 같은 민감한 값은 **환경 변수**에 둡니다
2. 겹치지 않고 뜻이 분명한 이름으로 **네임스페이스를 정합니다**
3. **인증 조건을 분명히 적어 둡니다**
4. 도움이 되는 메시지를 담아 **오류 응답을 제대로 돌려줍니다**
5. 가능하면 **응답을 캐시**해 속도를 높입니다
6. 컴포넌트에 테마가 여럿이라면 **스타일 변형을 지원합니다**

## Troubleshooting

### Resources not found

- 레지스트리 주소가 맞고 닿는지 확인합니다
- 주소에 `{name}` 자리표시자가 있는지 봅니다
- 그 자원이 레지스트리에 있는지 확인합니다
- 자원 종류가 레지스트리가 제공하는 것과 맞는지 봅니다

### Authentication issues

- 환경 변수가 제대로 설정됐는지 확인합니다
- API 키나 토큰이 유효하고 만료되지 않았는지 봅니다
- 헤더가 올바른 형식으로 전송되는지 봅니다

### Dependency conflicts

- 여러 레지스트리에 이름이 같은 자원이 있는지 살핍니다
- 모호하지 않도록 `@namespace/resource` 처럼 전체 이름을 씁니다
- 레지스트리 사이에 순환 의존성이 있는지 확인합니다
- 레지스트리를 섞어 쓸 때 자원 종류가 맞는지 봅니다
